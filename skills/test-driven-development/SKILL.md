# Test-Driven Development：测试驱动开发（TDD）

## 概述

先写测试。看它失败。写最小代码通过。

**核心原则：如果没有看着测试失败，你不知道它是否测试了正确的东西。**

**违反规则的字面规定，就是违反其精神。**

## 何时使用 | When to Use

**始终使用：**
- 新功能
- Bug 修复
- 重构
- 行为变更

**例外（询问你的搭档）：**
- 一次性原型
- 生成的代码
- 配置文件

想"这次跳过 TDD"？停。这是合理化。

## 铁律 | The Iron Law

```
未经失败的测试，不得编写生产代码
（NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST）
```

在测试之前写代码？删掉它。从头开始。

**没有例外：**
- 不要保留它作为"参考"
- 不要在写测试时"调整"它
- 不要看它
- 删除意味着删除

从测试全新实现。就是这样。

## 红-绿-重构 | Red-Green-Refactor

### RED — 写失败的测试

写一个最小的测试，展示应该发生什么。

**要求：**
- 一个行为
- 清晰的名字
- 真实代码（除非不可避免否则不用 mock）

### Verify RED — 看它失败

**强制要求。永远不要跳过。**

```bash
npm test path/to/test.test.ts
```

确认：
- 测试失败（不是错误）
- 失败消息符合预期
- 因为功能缺失而失败（不是拼写错误）

**测试通过了？** 你在测试已有行为。修复测试。

**测试错误？** 修复错误，重新运行直到正确失败。

### GREEN — 最小代码

写最简单的代码来通过测试。

不要添加功能、重构其他代码，或超出测试需要"改进"。

### Verify GREEN — 看它通过

**强制要求。**

```bash
npm test path/to/test.test.ts
```

确认：
- 测试通过
- 其他测试仍然通过
- 输出干净（无错误、无警告）

**测试失败？** 修复代码，不是测试。

**其他测试失败？** 现在修复。

### REFACTOR — 清理

只有在 green 之后：
- 消除重复
- 改进名字
- 提取辅助函数

保持测试 green。不要添加行为。

### 重复

下一个功能的下一个失败测试。

## 好测试 | Good Tests

| 质量 | 好 | 坏 |
|------|------|------|
| **最小** | 一件事。名字里有"和"？拆分。 | `test('验证邮箱和域名和空格')` |
| **清晰** | 名字描述行为 | `test('test1')` |
| **显示意图** | 展示期望的 API | 掩盖代码应该做什么 |

## 为什么顺序重要 | Why Order Matters

**"我之后写测试来验证它 work"**

代码后写的测试立即通过。立即通过什么都证明不了：
- 可能测试了错误的东西
- 可能测试实现，而不是行为
- 可能遗漏你忘记的边界情况
- 你从未见过它捕获 Bug

测试优先强迫你看着测试失败，证明它实际测试了某些东西。

## 常见合理化借口 | Common Rationalizations

| 借口 | 现实 |
|------|------|
| "太简单不需要测试" | 简单代码也会坏。测试只需 30 秒。 |
| "我之后测试" | 测试立即通过什么都证明不了。 |
| "之后测试能达到同样目标" | 之后测试 = "这做什么？" 测试优先 = "这应该做什么？" |
| "已经手动测试了" | 手动 ≠ 系统化。无记录，无法重跑。 |
| "删除 X 小时是浪费" | 沉没成本谬论。保留无法信任的代码是技术债。 |
| "保留作为参考，先写测试" | 你会调整它。这是之后测试。删除意味着删除。 |
| "需要先探索" | 可以。扔掉探索，从 TDD 开始。 |
| "测试难 = 设计不清" | 听测试的。难测试 = 难使用。 |
| "TDD 会拖慢我" | TDD 比调试更快。务实 = 测试优先。 |
| "手动测试更快" | 手动不能证明边界情况。每次变更你都会重新测试。 |
| "现有代码没有测试" | 你在改进它。为现有代码添加测试。 |

## 红牌警告 - 停，从头开始 | Red Flags - STOP and Start Over

- 代码先于测试
- 实现后写测试
- 测试立即通过
- 不能解释为什么测试失败
- 之后添加测试
- "就这一次"合理化
- "我已经手动测试了"
- "之后测试能达到同样目的"
- "这是精神不是仪式"
- "保留作为参考"或"调整现有代码"
- "已经花了 X 小时，删除是浪费"
- "TDD 是教条，我在变得务实"
- "这次不一样因为..."

**所有这些意味着：删除代码。用 TDD 从头开始。**

## 调试集成 | Debugging Integration

发现 Bug？写一个重现它的失败测试。遵循 TDD 周期。测试证明修复并防止回归。

永远不在没有测试的情况下修复 Bug。

## 验证检查清单 | Verification Checklist

在标记工作完成之前：

- [ ] 每个新函数/方法都有测试
- [ ] 在实现之前看着每个测试失败
- [ ] 每个测试失败原因符合预期（功能缺失，不是 typo）
- [ ] 写了最小代码来通过每个测试
- [ ] 所有测试通过
- [ ] 输出干净（无错误、无警告）
- [ ] 测试使用真实代码（除非不可避免否则不用 mock）
- [ ] 覆盖边界情况和错误

不能勾选所有框？你跳过了 TDD。从头开始。

## 最终规则 | Final Rule

```
生产代码 → 测试存在且先失败
否则 → 不是 TDD
```

没有搭档的许可不得有例外。
