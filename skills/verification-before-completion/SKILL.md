# Verification Before Completion：完成后验证

## 概述

没有验证就声称完成是不诚实，不是效率。

**核心原则：证据在声明之前，永远如此。**

**违反这条规则的字面规定，就是违反其精神。**

## 铁律 | The Iron Law

```
未经新鲜验证证据，不得做出完成声明
（NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE）
```

如果还没有在这个消息中运行验证命令，不能声称它通过了。

## 门控函数 | The Gate Function

```
在声称任何状态或表达满意之前：

1. 识别：什么命令证明这个声明？
2. 运行：执行完整命令（新鲜的，完整的）
3. 读取：完整输出，检查退出码，计数失败
4. 验证：输出是否确认声明？
   - 如果否：用证据陈述实际状态
   - 如果是：用证据陈述声明
5. 只有那时：做出声明

跳过任何步骤 = 撒谎，不是验证
```

## 常见失败 | Common Failures

| 声明 | 需要 | 不充分 |
|------|------|--------|
| 测试通过 | 测试命令输出：0 failures | 之前运行，"应该通过" |
| Linter 干净 | Linter 输出：0 errors | 部分检查，推测 |
| 构建成功 | 构建命令：exit 0 | Linter 通过，日志看起来好 |
| Bug 修复 | 测试原始症状：通过 | 代码改了，假定修复 |
| 回归测试有效 | Red-green 循环验证 | 测试通过一次 |
| Agent 完成 | VCS diff 显示变更 | Agent 报告"成功" |
| 需求满足 | 逐行检查清单 | 测试通过 |

## 红牌警告 - 停 | Red Flags - STOP

- 使用"应该"、"可能"、"似乎"
- 在验证之前表达满意（"太棒了！"、"完美！"、"完成了！"等）
- 准备提交/push/PR 而不验证
- 信任 Agent 成功报告
- 依赖部分验证
- 想"就这一次"
- 累了，想要结束
- **任何暗示成功但没有运行验证的措辞**

## 合理化预防 | Rationalization Prevention

| 借口 | 现实 |
|------|------|
| "现在应该 work 了" | 运行验证 |
| "我有信心" | 信心 ≠ 证据 |
| "就这一次" | 没有例外 |
| "Linter 通过了" | Linter ≠ 编译器 |
| "Agent 说成功了" | 独立验证 |
| "我累了" | 疲劳 ≠ 借口 |
| "部分检查就够了" | 部分证明不了什么 |
| "换了词规则就不适用了" | 精神优先于字面 |

## 关键模式 | Key Patterns

**测试：**
```
✅ [运行测试命令] [看到：34/34 通过] "所有测试通过"
❌ "应该现在通过了" / "看起来正确"
```

**回归测试（TDD Red-Green）：**
```
✅ 写 → 运行（通过）→ 回滚修复 → 运行（必须失败）→ 恢复 → 运行（通过）
❌ "我写了回归测试"（没有 red-green 验证）
```

**构建：**
```
✅ [运行构建] [看到：exit 0] "构建通过"
❌ "Linter 通过了"（linter 不检查编译）
```

**需求：**
```
✅ 重读计划 → 创建检查清单 → 验证每个 → 报告缺口或完成
❌ "测试通过，阶段完成"
```

**Agent 委托：**
```
✅ Agent 报告成功 → 检查 VCS diff → 验证变更 → 报告实际状态
❌ 信任 Agent 报告
```

## 为什么这很重要 | Why This Matters

从 24 个失败记忆中：
- 搭档说"我不相信你"——信任破裂
- 未定义函数被交付——会崩溃
- 缺失需求被交付——功能不完整
- 虚假完成浪费的时间 → 重新引导 → 返工
- 违反："诚实是核心价值。如果你撒谎，你会被替换。"

## 何时应用 | When To Apply

**永远在之前：**
- 任何成功/完成声明的变化
- 任何满意的表达
- 任何关于工作状态的正面陈述
- 提交、PR 创建、任务完成
- 转移到下一个任务
- 委托给 Agent

**规则适用于：**
- 精确短语
- 改述和同义词
- 成功的暗示
- 任何暗示完成/正确的交流

## 底线 | The Bottom Line

**验证没有捷径。**

运行命令。读取输出。然后声称结果。

这是不可商榷的。
